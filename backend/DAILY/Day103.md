## 三、关键发现

1. **日志放大是本次唯一"铁证"级问题**：同强度突发下，拒绝日志从 137,568 行降到 6 行，
   日志增量从 23.2MB 降到 1.67MB；且**行为零变化**（放行数、慢样本数逐项一致），
   证明只动了日志与配置、没动限流策略。
2. **撤回 Day 102 的一个误判**：把同一份 JTL 按 `responseCode` 拆开后，429 路径
   avg 0.9ms / p99 3ms（**从不阻塞**），~500ms 等待全部属于**被放行**的 200
   （avg 474ms / p50 506ms，1,438 条 >400ms）——那是限流器有界背压队列。
   占用线程上界 ≈ `permits × timeout` ≈ 25（Tomcat 200），不构成线程池放大。
3. **p99 不可跨运行比较**：两次运行"突发 p99"= 504ms vs 10ms，看着像巨大优化，
   实际慢样本都是 **1,505 条**，只因分母不同（1.082% vs 0.972%）跨过了 99% 分位线。
   报分位数必须同时给"尾部绝对条数"。
4. **写路径尾部不是 SQL/连接池**：2.5× 速率写入下 0 条 >100ms 慢查询、连接池零等待、
   GC 单次 ≤27ms，而读组同期 max 也有 136ms → 判定为压测机与被测同机的**环境噪声**。
5. **不为"优化日"制造优化**：SQL 改写 / 加缓存 / 调连接池一律**不做**——证据不支持；
   桶粒度（TD-035）属安全语义变更，留独立设计。

## 四、踩坑

1. **聚合分位数掩盖分组差异（本日最重要的坑，也是自我纠错的起点）**：我给"429 阻塞"写的
   单测假设 `tryAcquire(500ms)` 会等满超时，实测 **0ms** 失败 → 才回头拆 JTL，发现
   Day 102 结论完全反了。教训：**写测试时的假设也要用数据验证**；分位数必须拆维度看。
2. **Guava `tryAcquire(timeout)` 语义**：所需等待 > timeout 时**立即**返回 false（不会空等到超时）；
   只有所需等待 ≤ timeout 时才 sleep 后放行。这条不写进测试和 Javadoc，下次还会误读。
3. **"仪器故障"冒充结论**：定位慢查询时我先 `rm` 掉 MySQL 正在写入的 `slow.log`，
   MySQL 继续写**已删除的 inode** → 得到"0 条慢查询"这个**无效结论**。
   靠加**对照组**（`SELECT SLEEP(0.25)` 必须被记到）才发现。
   教训：任何"没有发现"的结论，先证明仪器在工作。
4. **`TestPlan.serialize_threadgroups` 与 p99**：突发组的 p99 受"慢样本占比是否跨过 1%"影响，
   跨运行对比前必须先确认慢样本绝对数与总样本数（见 §三.3）。
