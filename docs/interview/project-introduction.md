## 三、3 分钟完整口述稿

### 0:00-0:20 定位

> 我做的是一个工业 AI 设备管理平台，目标不是单独展示某个框架，而是把设备接入、业务管理、AI 分析、异步推送和运维观测串成一条可运行的链路。后端是 Java 25、Spring Boot 3.5 和 MyBatis，前端是 Vue 3，基础设施用 Docker Compose。

### 0:20-0:55 业务范围

> 平台覆盖认证与 RBAC、站点数据隔离、设备和遥测数据、报警工作流、操作审计，以及 AI 问答和巡检。系统的核心数据流有两条：第一条从设备遥测进入时序数据，再触发规则报警和下行控制；第二条从 Agent 生成巡检日报，经 RabbitMQ、Redis 幂等后，通过 SSE 推送到浏览器。

### 0:55-1:45 真实硬件闭环

> IoT 部分我没有停在模拟器。真实 ESP32-S3 接 DHT22，每两秒通过 MQTT QoS1 上报。后端 Paho Listener 消费后，用设备 ID、时间戳和字段类型组成 Redis SETNX 幂等键，避免 QoS1 重投造成重复数据，然后写 MySQL 并进入报警规则。命中温度或湿度阈值时，后端向 command Topic 下发继电器命令，Redis 做 5 秒节流，固件吸合 3 秒后自动复位。
>
> 真机实测时，静置基线是 29 度、52% 湿度；哈气到 100% 湿度触发 `OVER_HUMIDITY`，热风到 68 度触发 `OVER_TEMP`，停止后恢复到约 30 度、49.7% 湿度。温度、湿度两个分支都走通了“传感器到 Broker、后端、规则、执行器”的完整物理回路。

### 1:45-2:30 AI、异步与观测

> AI 部分不是只接一个聊天接口，而是落到五个业务价值：告警摘要、设备健康诊断、基于 PDF 知识的 RAG 问答、MCP 加 Agent 的巡检日报，以及把巡检异常自动转成业务报警。Agent 用手动循环限制 3 到 6 轮，MCP 只暴露 7 个只读工具。DeepSeek 是可选依赖，没配置 API Key 时 AI 返回 503，但设备、报警等核心业务继续运行。
>
> 巡检日报生成后走 RabbitMQ，失败进 DLQ；消费端用 Redis 幂等，再通过 SSE 推给指定站点的浏览器。观测上有 Prometheus 业务指标、全链路 traceId 和滚动日志。

### 2:30-3:00 结果、取舍与收获

> 质量基线是 375/375 测试。JMeter 实测读接口 40.3 req/s、p99 18 毫秒，写接口 100% 落库；4639 req/s 突发下限流拒绝率 98.87%，14.2 万个样本的 traceId 回传零失败。我最大的收获是工程判断不能靠感觉：压测后发现限流日志被放大，我只修有证据的日志问题，日志量下降 92.8%，但没有无证据地改 SQL、缓存或连接池。这个项目让我能把一项功能从代码正确性推进到真实链路、性能证据和可运维性。

## 四、10 分钟完整口述稿

### 0:00-1:00 背景与目标

> Industrial AI Hub 是一个工业设备管理与 AI 分析平台。我把它作为一次完整工程训练：从 Java 基础和 Spring Boot，到 Redis、RabbitMQ、Docker，再到 AI、MCP、MQTT 和真实硬件。
>
> 我给自己定的目标有三个。第一，业务必须闭环，不能只做页面和接口；第二，关键结论必须有测试或实测证据；第三，对没有完成的能力要明确边界。最终项目形成 37 份 ADR、375 个后端测试、14 个活动数据库迁移和一套 Docker Compose 编排，并在真实 ESP32 上完成了温湿度和继电器闭环。

### 1:00-2:30 架构与数据链路

> 系统采用前后端分离。浏览器通过 REST 调后端，认证链路使用 JWT，权限模型是 ADMIN、OPERATOR、VIEWER 三级角色，同时叠加站点资源作用域。也就是说，有权限不代表能看所有站点，非管理员只能访问被授权站点的数据。
>
> 后端仍是 Controller、Service、Mapper 分层，统一响应和全局异常处理，AOP 记录关键操作审计。基础设施方面，MySQL 存业务与时序数据，Flyway 管理 Schema；Redis 承担缓存、分布式锁、幂等和命令节流；RabbitMQ 承担报警与巡检的异步链路；EMQX 负责 MQTT；Prometheus 拉取 Actuator 指标。
>
> 我有意把 MQTT 和 RabbitMQ 分开。MQTT 面向资源受限设备和不可靠网络，负责设备接入、QoS 和遗嘱消息；RabbitMQ 面向后端内部任务分发、重试和 DLQ。让它们各自做擅长的事，比强行用一个中间件覆盖两个领域更清晰，这个取舍记录在 ADR 0033。

### 2:30-4:30 IoT 物理闭环

> 上行链路从 ESP32-S3 和 DHT22 开始。固件连接 WiFi 和 EMQX，每两秒发布一条 QoS1 telemetry，Topic 使用 `plc/{siteCode}/{deviceCode}/telemetry`，同时发布 retained 在线状态和 LWT 离线状态。
>
> 后端 Paho Listener 使用 SmartLifecycle 管理连接，订阅 QoS1。收到消息后先校验 Topic、设备码、时间戳和字段，再用 `mqtt:{deviceId}:{ts}:{dataType}` 作为字段级幂等键，通过 Redis SETNX 加 24 小时 TTL 去重。QoS1 的语义是至少一次，所以重复消息是正常现象，不能假设只会消费一次。
>
> 落库后系统广播数据并执行报警规则。温度或湿度超限时，报警链路会向 command Topic 下发 `RELAY_ON`。下行也有两道约束：后端用 Redis 做 5 秒节流，固件收到后吸合 3 秒自动复位，这样即使短时间重复报警，执行器也不会被无限触发。
>
> 真机验证不是“看到日志”就结束，而是同时确认三件事：设备消息持续进入、数据库持续新增、规则报警能驱动继电器。静置 29 度、52% 湿度；哈气到 100% 湿度触发 `OVER_HUMIDITY`；热风到 68 度触发 `OVER_TEMP`；停止后恢复到约 30 度、49.7%。这才算物理闭环。

### 4:30-6:00 AI、RAG、Agent 与 MCP

> AI 部分我一直用业务价值衡量，不用“接入了大模型”衡量。第一类是告警摘要，把多条报警压缩成可读结论；第二类是设备健康诊断，根据近期数据给出风险和建议；第三类是 RAG 知识库问答，PDF 被解析、切片、向量化和 Top-K 检索，回答带引文；第四类是巡检日报，Agent 通过 MCP 工具查询设备和数据；第五类是巡检发现异常后自动生成业务报警，这是 AI 和业务系统的真正闭环。
>
> Agent 治理上我没有使用无上限自动循环，而是手动执行工具调用，并关闭 Spring AI 的 internal tool execution。普通设备分析默认 3 轮，复杂巡检最多 6 轮，达到上限就强制收尾。MCP 只暴露 7 个只读查询工具，写业务动作仍由后端受控服务完成。
>
> 这里也要讲清边界。当前 RAG 使用 `SimpleVectorStore` 和本地哈希 Embedding，适合打通链路和单机验证，不是已经接入 Qdrant；生产级向量库仍是演进项。DeepSeek 也是 opt-in，未启用时 AI 返回明确的 503，核心设备与报警功能不受影响。

### 6:00-7:00 安全、异步与 SSE

> 安全方面除了 JWT 和 RBAC，还做了登录失败治理、Token 黑名单、操作审计和站点隔离。AI、MCP、SSE 这些高成本或长连接入口有独立限流和访问边界；SSE 允许 query token，但仅限这个端点，普通 REST 不读取 URL 中的 token，避免日志泄漏。
>
> 巡检日报链路是 Agent 生成结果后，生产者投递 RabbitMQ；Consumer 手动 ACK，失败时 nack 且不重新入队，进入 DLQ；成功消费前用 Redis SETNX 做跨实例幂等；Push Gateway 再按用户可访问站点筛选 SSE 会话。浏览器断开时清理会话，发送失败也只移除失效连接，不阻塞其他用户。
>
> 这条链路有真实 RabbitMQ 和 Redis 的集成测试，但必须通过 `RUN_INSPECTION_IT=true` 显式触发。浏览器级 SSE E2E 还没有补，这是当前明确的测试缺口，我不会把“单测通过”说成“浏览器全链路已验证”。

### 7:00-8:00 观测、测试与性能证据

> 观测层有三部分。Prometheus 除 JVM 和 HTTP 指标外，还有三条业务指标：MQTT 消费结果、报警触发、继电器命令结果。HTTP 请求有 traceId，从最外层 Filter 写入 MDC 和响应头，支持跨请求透传；日志按时间与大小滚动，ERROR 单独归档。
>
> 性能方面，JMeter 在限速内实测读接口 40.3 req/s、平均 8.5 毫秒、p99 18 毫秒，2415 个样本全部 200；写接口 20.1 req/s、全部落库。突发时 JMeter 施压约 4639 req/s，系统按设计放行约 52.5 req/s，拒绝率 98.87%。14.2 万个样本，包括大量 429，traceId 回传断言零失败。
>
> 测试基线是 375/375。这个数字不是唯一质量指标，所以我更看重测试与哪些风险对应：MQTT 幂等有 17 个服务测试，SSE/RabbitMQ 链路有真实中间件 IT，限流日志节流有 9 个专项测试，Compose 能力则在容器网络重新验证。

### 8:00-9:15 两个工程难点故事

> 第一个故事是自我纠错。第一次压测时，我把突发请求约 500 毫秒的 p99 归因于限流 `tryAcquire` 阻塞。第二次我没有直接优化，而是按响应码拆分同一份 JTL。结果 429 的平均响应只有 0.9 毫秒、p99 3 毫秒，真正等待的是被放行进入背压队列的 200。还有一个陷阱：优化后“突发 p99”从 504 毫秒降到 10 毫秒，看起来很好，但两个版本慢样本绝对数都是 1505，只是占比跨过了 1% 分位线。这让我以后报 p99 时必须同时给尾部和绝对条数。
>
> 第二个故事是订阅端静默断连。一次演示前冒烟，MQTT 发布端没有报错，但数据库增量为 0。排查后发现后端旧连接 keepAlive 写超时后，Paho 没有恢复到可消费状态。修复方式不是只重启进程，而是重启后明确检查 `MQTT Listener connected`，再让模拟器发布 15 秒，确认数据库增加 44 条。联调不能只看发送成功，必须同时证明订阅端在线和业务落库。

### 9:15-10:00 边界、改进与总结

> 我也很清楚当前边界。RAG 还不是生产向量库；SSE 缺浏览器级 E2E；SSE 会话注册表、限流桶和日志节流仍是单 JVM 状态，虽然 Redis 幂等能跨实例，但系统还不能宣称无状态任意扩容；报警风暴的合并去重也还没完成。
>
> 下一步优先级会按风险来：先把 SSE 和报警风暴补上，再把会话、限流和向量库做成可水平扩展；最后补容器化前端、Grafana 与镜像源治理。这个项目对我最大的价值不是用了多少技术，而是形成了“契约先行、真实链路验证、用数据下结论、对边界诚实”的工程方法。

## 五、高频追问与回答要点

| 追问 | 回答骨架 | 可追问证据 |
|------|----------|------------|
| 为什么同时用 MQTT 和 RabbitMQ？ | MQTT 面向设备接入与不稳定网络，RabbitMQ 面向后端任务、DLQ 与重试；边界见 ADR 0033 | `docs/decision-log/0033-emqx-mqtt-broker.md`、`0023/0031` |
| QoS1 重复消息怎么办？ | 接受“至少一次”语义，用字段级 Redis SETNX 幂等；键包含设备、时间戳、字段类型，TTL 24h | `MqttDeviceDataIngestServiceTest` 17 用例 |
| Redis 挂了会不会阻断数据？ | 幂等异常按降级策略继续落库，不因缓存故障吞掉真实遥测；代价是可能重复，需要唯一约束或后续补偿兜底 | Day 96 日志、ADR 0034 |
| AI 挂了业务是否不可用？ | DeepSeek 是 opt-in；未启用或调用失败返回 503/降级结果，设备、报警链路照常运行 | ADR 0021、Day 107 演示降级路径 |
| RAG 用了 Qdrant 吗？ | 没有。当前是 `SimpleVectorStore + LocalHashEmbeddingModel`，接口已抽象，Qdrant 是演进目标 | ADR 0024、工程踩坑手册 |
| Agent 如何防止死循环和乱调用？ | 手动循环关闭框架自动工具执行；普通 Agent 3 轮、巡检最多 6 轮；MCP 仅 7 个只读工具；操作日志记录轮次与调用数 | ADR 0023/0026/0027 |
| SSE 如何防重复、丢消息、连接泄漏？ | RabbitMQ 消费幂等、手动 ACK、失败 DLQ；Push Gateway 只移除失效会话；30 分钟超时与生命周期回调清理 | ADR 0031/0032 |
| 系统能水平扩容吗？ | 不能简单回答“能”。Redis 幂等可跨实例，但 SSE Registry、Guava 限流和日志节流仍是 per-JVM，多副本改造未完成 | ADR 0031 §4.1、ADR 0037 |
| 为什么写接口 p99 有 175.9ms？ | 先承认尾部抖动；随后用 2.5 倍速率复测，1506 次写入 100% 成功、0 条超过 100ms 慢 SQL，Hikari pending 0，GC pause 最大 27ms，判为同机压测环境噪声 | Day 103 报告 |
| 为什么没有加缓存、改 SQL、调连接池？ | 证据不支持。优化动作应针对已证明的瓶颈；Day 102 的真实放大器是限流拒绝日志，因此只做日志节流，行为保持不变 | ADR 0037 |
| 375 个测试是否等于高质量？ | 不等于。数字只说明当前回归范围；关键是风险映射，包括真实 RabbitMQ/Redis IT、MQTT 幂等矩阵、限流并发与大样本 traceId 守卫 | README 质量表、Day 91/103 |
| 数据库为什么是 10 张表、14 个活动迁移？ | 以 Flyway 文件为 SSOT；V2 已退役，当前是 V1 + V3-V15，Schema 版本 V15。演示种子与生产链隔离 | ADR 0012/0019、SQL README |
| Compose 是否整合成微服务？ | 没有。当前是模块化单体加 15 服务编排，Nacos、MinIO、ES 等属于 full-profile 基础设施验证，不代表业务已拆微服务 | Baseline V1.6、README |

### 回答追问时的三个避免

1. **避免把压测施压值当吞吐能力**：4639 req/s 是输入压力，系统按设计放行约 52.5 req/s。
2. **避免把 opt-in 能力说成默认在线**：DeepSeek 默认关闭，RAG 未接生产向量库，full-profile 不随默认启动。
3. **避免把单机能力说成分布式能力**：Redis SETNX 幂等支持跨实例，不等于 SSE、限流和日志状态已经可水平扩展。

## 六、可展开的工程故事

### 故事一：用响应码拆分，撤回自己的性能误判

**背景**：Day 102 压测中，突发流量出现约 500ms 的 p99。我最初把它归因于限流拦截器的 `tryAcquire(500ms)`。

**行动**：没有直接删等待或改线程池，而是拿同一份 JTL 按 `responseCode` 拆分。429 平均 0.9ms、p99 3ms；约 500ms 的等待发生在被放行的 200 上，是限流后的有界背压队列。

**结果**：撤回错误结论。后续优化只处理有证据的日志放大器：拒绝日志从 137,568 行降到 6 行，体积下降 92.8%，放行与慢样本数量逐项一致。

**反思**：分位数必须结合慢样本绝对数。Day 103 的“突发 p99 从 504ms 降到 10ms”并不是行为改善，慢样本仍是 1505 条，只是跨过了 1% 分位线。

### 故事二：发布端正常，不代表后端还在消费

**背景**：Day 107 演示环境冒烟时，模拟器发送正常，但 `device_data` 增量为 0。

**行动**：依次核对 Broker、订阅端连接、后端日志与数据库水位，定位到旧 Paho 连接在 keepAlive 写超时后没有恢复到可消费状态。优雅重启后端，并显式检查 `MQTT Listener connected`。

**结果**：再次发布 15 秒，数据库新增 44 条，证明订阅与落库同时恢复；同时确认演示无硬件 B 路径可用。

**反思**：联调的验收必须是“发布端确认 + 订阅端在线 + 数据库增量”，只看到发送 API 不抛异常不算端到端成功。

### 故事三：拒绝无证据的优化

**背景**：写接口尾部延迟有波动，直觉上容易想到 SQL、缓存或连接池。

**行动**：在 2.5 倍写入速率下复测，并设置带 `SELECT SLEEP(0.25)` 的对照组验证慢查询仪器；同时查看 Hikari pending、连接获取时间和 GC pause。

**结果**：1506 次写入全部成功，0 条超过 100ms 的慢 SQL，Hikari pending 为 0，GC pause 最大 27ms。尾部抖动与同机压测噪声一致，因此不做无证据的架构改动。

**反思**：“优化了什么”容易汇报，“基于什么证据决定不优化”更能体现工程判断。
