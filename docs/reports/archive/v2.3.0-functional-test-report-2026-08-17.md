## 2. 首轮功能测试发现（3 个真实缺陷 + 3 个测试过期项）

### 2.1 真实缺陷（已在 pc_hula 修复）

| # | 缺陷 | 现象 | 根因 | 修复 |
|:-:|------|------|------|------|
| D1 | `GET /api/users/{id}`、`GET /api/devices/{id}` 返回 **500** | 测试 `按 ID 查询` 全挂 | `CacheConfig` 的 `GenericJackson2JsonRedisSerializer` 默认 ObjectMapper **未注册 JavaTimeModule**，`@Cacheable` 写缓存时 `LocalDateTime` 序列化失败（`SerializationException`） | `CacheConfig.java`：构造带 `JavaTimeModule` 的 ObjectMapper（关闭 WRITE_DATES_AS_TIMESTAMPS） |
| D2 | 操作日志静默丢失 | `OperationLogAspect` 报 `Check constraint 'chk_operation_type' is violated` | `AlarmController.acknowledge/resolve` 的 `@OperationLog(operationType="ACKNOWLEDGE"/"RESOLVE")` 不在 V1 CHECK（仅 CREATE/UPDATE/DELETE/LOGIN/EXPORT）允许范围 | 新增 **Flyway V3** `V3__operation_log_check_types.sql` 扩展 CHECK；修复后 `operation_log` 成功落库 ACKNOWLEDGE/RESOLVE |
| D3 | 管理员可删除自己 | `DELETE /api/users/1` 返回 200，admin 被软删（`is_deleted=1`） | `UserService.delete` / `UserController.delete` **无自删保护** | `UserController.delete` 增加守卫：删除当前登录用户 → `400 不能删除当前登录用户`（与测试集契约一致） |

## 6. 审查反馈复修（第二轮，2026-08-18）

团队审查指出 **D1 修法不完整**：`GenericJackson2JsonRedisSerializer(ObjectMapper)` 不会自动写入类型信息，缓存**读命中**时反序列化为 `LinkedHashMap` → `ClassCastException` → 同一 ID 第二次请求 500。已实证复现（`ClassCastException: LinkedHashMap cannot be cast to UserVO`）并修复：

### 6.1 修复内容

| # | 反馈项 | 处置 |
|:-:|--------|------|
| P1 | D1 补类型信息（读命中 500） | `CacheConfig.createCacheObjectMapper()`：`activateDefaultTyping(NON_FINAL)` 写入 `@class`；**校验器用受限 `BasicPolymorphicTypeValidator`**（仅放行 `dev.reboot.dto/entity` + JDK 集合/时间/数值），比审查建议的 LaissezFaire 更安全（遵循仓库 RedisConfig 安全备忘，未重新引入无限制反序列化风险） |
| P2-2 | 0012 changelog 未同步 | 新增 V1/V2/V3 变更行 + "当前 Schema 由 Flyway 管理"说明 |
| P2-3 | 单测盲区 | 新增 `CacheSerializationTest`（3 用例：UserVO/DeviceVO/List 往返还原原类型 + `@class` 断言）；`UserServiceTest` 补 `delete_shouldRejectDeletingSelf`（400 自删守卫） |
| P3-4 | 自删守卫跳层 | 业务规则下沉 `UserService.delete(id, currentUserId)`（Controller 仅从 request 提取 userId 传入） |
| P3-6 | 自删返回码 | 维持 `400 BAD_REQUEST`（与测试集契约一致；403 语义可选，未改） |
