## 四、更正：Day 102 关于"429 阻塞 500ms"的误判

Day 102 报告初版称：`tryAcquire(500ms)` 让**被拒请求**阻塞线程，突发 p99 504ms 即超时镜像。
把同一份 JTL 按 `responseCode` 拆开后：

| 突发组响应码 | 样本 | avg | p50 | p95 | p99 | max | >400ms |
|---|---:|---:|---:|---:|---:|---:|---:|
| **429（拒绝）** | 137,568 | **0.9ms** | 1ms | 2ms | **3ms** | 65ms | **0** |
| **200（放行）** | 1,575 | 474ms | 506ms | 512ms | 527ms | 573ms | 1,438 |

- 被拒路径**从不阻塞**（无一条 >100ms）；
- ~500ms 等待全部属于**被放行**的请求 = Guava 有界背压队列的正常行为；
- 占用线程上界 ≈ `permits × timeout` = 50/s × 0.5s ≈ **25**（Tomcat 200），不构成线程池放大。

**附带发现的统计陷阱**：两次运行的"突发 p99"分别为 504ms 与 10ms，看着像巨大改善，
实际**绝对行为完全没变**——慢样本都是 1,505 条，只是分母不同：

```text
Day 102：1,505 / 139,143 = 1.082%  > 1% → p99 落在慢样本内 → 504ms
Day 103：1,505 / 154,871 = 0.972%  < 1% → p99 落在快样本内 →  10ms
```

即 **p99 在小样本/边界占比下不可跨运行比较**，必须连同"慢样本绝对条数"一起看。
该教训已写入 ADR 0037 与 Day102.md 更正块。

## 五、写路径尾部（p99 176ms）定位结论

用实例自带的 Micrometer 指标 + **带对照组的** MySQL 慢查询日志定位，结论：**不是 SQL、不是连接池**。

### 5.1 指标证据（60s / 20 req/s 写入窗口）

| 维度 | 指标 | 实测 | 判读 |
|------|------|------|------|
| 连接获取 | `hikaricp_connections_acquire_seconds_max` | **8ms** | 无池争用 |
| 池排队 | `hikaricp_connections_pending` | **0** | 无等待线程 |
| 连接持有（含 SQL 执行） | `hikaricp_connections_usage_seconds_max` | 71ms | DB 交互上限，非 156ms 主体 |
| GC | `jvm_gc_pause_seconds_max`（G1 Young） | **27ms** | 单次暂停不足以解释尾部 |
| MQ 发布 | `rabbitmq_published_total` | 1,207 = 写入数 | 1:1，无失败 |
| 读路径同期 | JMeter 读组 max | **136ms** | 与写组同量级 → 尾部是**共享性**的 |
| 写路径 max | Micrometer `...device-data..._max` | 156ms | 与 JMeter max 158ms 一致 |

### 5.2 慢查询核验（含对照组，避免"仪器故障冒充结论"）

第一次测量时我先 `rm` 掉了 MySQL 正在写入的 `slow.log`，MySQL 继续写已删除的 inode →
"0 条慢查询"**无效**。改用**对照组**验证仪器：

```text
1) SET GLOBAL slow_query_log=OFF→ON（重建文件）
2) 对照组：SELECT SLEEP(0.25) → slow.log 出现 1 条 Query_time: 0.255226  ✓ 仪器可信
3) 负载：30s / 50.2 req/s / 1,506 次写入（2.5× Day 102 速率，100% 200）
4) 结果：>100ms 慢查询 = 0 条（仅剩对照组那 1 条）
```

### 5.3 结论

- **SQL 不是瓶颈**：2.5× 速率写入下 0 条 >100ms 慢查询；写延迟 p99 **39ms**、max 84ms，
  反而优于 Day 102 的 20 req/s 场景（p99 176ms）——说明那次尾部是**间歇性环境噪声**
  （压测机与被测应用同机、JVM 调度 + GC + 偶发 DB 抖动），不是写路径缺陷；
- 因此**不做** SQL 改写 / 加缓存 / 调连接池——当前证据不支持，加了属于无靶射击；
- 残留验证手段（当需要进一步压缩尾部时）：把压测机移出被测主机、对写路径做分段计时埋点。

## 七、遗留

1. **TD-035**：限流桶仍是 per-path 全局单桶（单客户端可耗尽全站某路径配额）→ 需"全局桶 + 客户端桶"
   双层设计 + 独立 ADR + 安全评审，本日不做；
2. **TD-038**：`HttpMessageNotReadableException`（畸形 JSON）仍走兜底返回 **500**，语义应为 400；
3. 多实例下日志节流状态 per-JVM（与 Day 91 P1-2 多副本治理同源）：总量 ≈ 副本数 × 1 行/窗口，
   可接受，但若做集中日志（Day 101 ELK 触发条件）时需一并复核；
4. `AiRateLimitInterceptor` 仍逐条输出 429 日志（放大倍率低，未纳入本日）。
