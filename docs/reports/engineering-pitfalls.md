# Industrial AI Hub 工程踩坑手册

> 最后更新：2026-10-18 | 覆盖：Day 1-107 | 来源：每日日志、ADR、压测/性能报告、部署 Runbook

本手册按主题归并已经真实发生过的故障。每条统一使用四段：

**现象 -> 根因 -> 修复 -> 防再发规则**

目标不是收藏“错误答案”，而是把一次排障转成下一次可执行的检查顺序。

## 一、连接与生命周期

### 1. Paho `deliveryComplete` 空消息导致整条连接断开

- **现象**：MQTT 冒烟首轮投递回调触发 NPE，随后 `connectionLost`，客户端断连。
- **根因**：`token.getMessage()` 可能为 null，QoS 0 不保留消息，异步完成时也可能被清理。
- **修复**：回调中对消息做 null 判断，仅用 token/msgId 记录完成信号。
- **防再发规则**：所有异步回调入口先证明引用可空；回调异常不能污染连接生命周期。
- **来源**：Day 94，`docs/notes/mqtt-learning-notes.md` §11.3。

### 2. 相同 MQTT clientId 互踢

- **现象**：临时 8081 实例启动失败；EMQX 中常驻后端掉线，双实例不能同时消费。
- **根因**：8080 与 8081 共用 `iah-backend-mqtt`，Broker 按 clientId 保留唯一连接。
- **修复**：临时实例关闭 MQTT；容器部署使用独立 `MQTT_CLIENT_ID=iah-backend-container`。
- **防再发规则**：每实例 clientId 必须唯一；只验证 HTTP 的临时实例优先 `MQTT_ENABLED=false`。
- **来源**：Day 101、Day 104、ADR 0034。

### 3. MQTT 32002 静默断连，模拟器“正常”但数据不再入库

- **现象**：演示前模拟器运行成功，`device_data` 增量却为 0。
- **根因**：常驻后端 keepAlive 写超时 32002 后连接未自愈，模拟器仍有发送但无人订阅。
- **修复**：优雅停止旧进程并重启，确认 `MQTT Listener connected` 后复测增量 Δ+44。
- **防再发规则**：MQTT 联调先验证“订阅端在线 + 落库增量”，不能只看发布端无异常；演示前必做端到端冒烟。
- **来源**：Day 107。

### 4. Paho 客户端并发与持久化边界

- **现象**：学习代码并发 publish 时存在线程安全风险；QoS 1/2 未确认消息在 JVM 崩溃后可能丢失。
- **根因**：`MqttClient` 非线程安全；`MemoryPersistence` 不提供生产级持久化。
- **修复**：生产使用 `MqttDefaultFilePersistence`，并发场景使用 `MqttAsyncClient` 或串行化发送。
- **防再发规则**：连接、持久化、线程模型必须一起评审，不把 QoS 数字当成可靠的同义词。
- **来源**：Day 94-96，ADR 0034。

### 5. SSE 的 `complete()` 在无 Web 异步上下文时是 no-op

- **现象**：集成测试调用 `emitter.complete()` 后 registry 大小不变，无法证明回调清理。
- **根因**：Spring MVC 的 completion/timeout 回调依赖真实异步请求上下文。
- **修复**：`sendSafely`、30 分钟 timeout、`@PreDestroy` 三重兜底；把浏览器 E2E 留为专项。
- **防再发规则**：框架生命周期回调必须用真实运行环境验证，mock/单测不能替代 SSE 长连接证据。
- **来源**：Day 91 Exit Audit，ADR 0032 §4.1。

## 二、配置、密钥与环境

### 6. `.env` 与 IDEA Run Configuration 双事实源漂移

- **现象**：命令行正常，IDEA 启动却 Redis WRONGPASS 或 MQTT 变量缺失；换机器再次出现。
- **根因**：Run Configuration 手填旧密钥/旧变量，覆盖或绕过了根 `.env`。
- **修复**：清理 IDE 环境变量，统一由 `application-dev.yml -> spring.config.import` 读取根 `.env`。
- **防再发规则**：`.env` 是开发密钥 SSOT；敏感变量缺失 fail-fast；提交前 grep `.idea/` 和资源目录。
- **来源**：ADR 0015、Day 99。

### 7. Compose 空变量覆盖 Spring 默认值

- **现象**：Spring 配置 `${RATE_LIMIT_PERMITS:50}` 在容器中解析为空串，数值绑定失败或行为异常。
- **根因**：Compose `${VAR:-}` 注入了空环境变量；Spring 只对“变量不存在”使用默认值。
- **修复**：Compose 默认值与 `application.yml` 对齐，或不在缺失时注入空值。
- **防再发规则**：检查 `env | grep` 与 Compose `environment`，区分“未设置”和“设置为空”。
- **来源**：Day 104。

### 8. YAML 重复顶级键使 Spring 上下文整体失败

- **现象**：新增 Actuator 配置后 4 个 `@SpringBootTest` 上下文出现 7 个错误。
- **根因**：`application.yml` 已有 `management:`，新增第二个顶级段触发 SnakeYAML duplicate key。
- **修复**：合并进既有段，完整回归恢复。
- **防再发规则**：新增顶级键前先 `rg "^management:"`；配置改动先跑最小上下文测试。
- **来源**：Day 100。

### 9. Logback 类包名错误只在真实启动时爆炸

- **现象**：`LevelFilter` 配置导致应用 fail-fast，编译阶段却完全正常。
- **根因**：误用不存在的 `ch.qos.logback.core.filter.LevelFilter`；正确类在 `classic.filter`。
- **修复**：改为 `ch.qos.logback.classic.filter.LevelFilter`，用临时实例验证滚动与错误分流。
- **防再发规则**：XML/反射/SPI 配置不参与 Java 编译，必须真实启动验证。
- **来源**：Day 101。

### 10. Filter 进构造器但没有注册 Bean

- **现象**：TraceIdFilter 初版遗漏 `@Component`，6 个 Spring 测试上下文因依赖缺失失败。
- **根因**：`WebMvcConfig` 构造器注入要求 Filter 是容器 Bean。
- **修复**：补 `@Component`，增加生成/透传/超长防御测试。
- **防再发规则**：新增 Filter 时同时检查 Bean 注册、order 和 finally 清理 MDC。
- **来源**：Day 101。

## 三、数据、幂等与时间

### 11. 演示种子进入 Flyway 生产迁移链

- **现象**：全新生产库可能自动出现测试用户、50 台设备和告警。
- **根因**：`V2__seed_test_data.sql` 与 Schema 迁移同目录，被所有环境自动执行。
- **修复**：退役 V2，仅保留 V1 + V3 起的 Schema 链；演示数据移到 `db/seed/dev/` 并显式执行。
- **防再发规则**：迁移目录只放 Schema/必需初始化；种子必须与自动迁移物理隔离。
- **来源**：ADR 0019 §5，Flyway P0 修复。

### 12. QoS 1 重复投递造成重复业务写入

- **现象**：客户端重发或 Broker 重投时，同一传感器采样可能写入多行。
- **根因**：MQTT QoS 1 是 at-least-once，不保证消费端只处理一次。
- **修复**：Redis `SETNX mqtt:{deviceId}:{ts}:{dataType}`，TTL 24 小时，字段级幂等。
- **防再发规则**：所有 at-least-once 消费者按业务唯一键做幂等；幂等键必须包含设备、时间、数据类型。
- **来源**：Day 96，ADR 0034。

### 13. 时间戳丢时区或按本地时区猜测

- **现象**：设备上报时间与入库/查询时间偏移，跨时区窗口统计错位。
- **根因**：只解析 `LocalDateTime`，忽略 payload 中的 offset/timezone。
- **修复**：保留带时区时间并统一转换为业务时区；非法时间不落为“当前时间”掩盖数据错误。
- **防再发规则**：协议契约明确时间格式；测试覆盖无时区、带 offset、非法值和跨日边界。
- **来源**：Day 96，`MqttDeviceDataIngestServiceTest`。

### 14. 新审计类型未扩展 CHECK，业务成功但审计静默失败

- **现象**：RAG、MCP、巡检、推送、自动报警功能可用，对应 operation_log 插入被数据库拒绝。
- **根因**：`operation_log.operation_type/target_type` 是 CHECK 枚举，新增类型未同步迁移。
- **修复**：V3、V9-V15 逐步扩展枚举，并为每个新审计入口补契约测试。
- **防再发规则**：新增 `@OperationLog` 类型时，代码、H2 schema、Flyway CHECK、测试四处同步。
- **来源**：V3/V9-V15，ADR 0022/0023/0025/0029-0031。

### 15. 软删除后编码不能复用

- **现象**：删除设备后重新创建设备，唯一键仍冲突。
- **根因**：唯一键只包含 `device_code`，没有纳入 `is_deleted`。
- **修复**：V7 改为 `(device_code, is_deleted)`；role code 同理。
- **防再发规则**：采用逻辑删除的表，从设计时评审“业务键 + 删除位”的唯一性语义。
- **来源**：V7，数据库审计 DB-02。

### 16. 文档表数量与迁移事实漂移

- **现象**：多处写“9 张表”，实际 V1 的 7 张加 V4 两张、V6 一张，共 10 张。
- **根因**：新增 `login_audit` 后只更新了局部架构段落，索引/README/AGENTS 未全部同步。
- **修复**：Day 108 以迁移文件为 SSOT，统一为 10 表并补 `login_audit`。
- **防再发规则**：Schema 变更后同时更新 V 文件、ADR 0012、SQL README、根 README、AGENTS。
- **来源**：V1/V4/V6，Day 108 文档核对。

## 四、硬件与 IoT

### 17. 继电器从 GPIO5 改到 GPIO14

- **现象**：按早期教程接 GPIO5 与最终固件行为不一致。
- **根因**：固件按实拍 N16R8 板和布线便利性改为 GPIO14；旧教程未同步淘汰。
- **修复**：`RELAY_PIN=14`，GPIO14 与 5V0/GND 相邻便于三线成束。
- **防再发规则**：以固件常量、板子丝印和图册“引脚安全地图”三者交叉核对；只信最新标记。
- **来源**：Day 99，ADR 0035。

### 18. ESP32-S3-N16R8 的 PSRAM/特殊脚不可当普通 IO

- **现象**：接 GPIO35/36/37 后板子反复重启；接启动脚可能导致无法烧录。
- **根因**：35/36/37 被八线 PSRAM 占用，0/3/45/46 是 strapping，19/20 是 USB。
- **修复**：项目只用 GPIO4（DHT22）、6/7（I2C）、14（继电器）。
- **防再发规则**：接线前先看“引脚安全地图”和板子丝印，不照搬通用 ESP32 教程。
- **来源**：Day 99，硬件接线图册。

### 19. 热风不等于高湿度，测试条件选错会误判传感器

- **现象**：热风吹 DHT22 得到 68°C/10.9%RH，湿度报警不触发。
- **根因**：相对湿度随温度升高而降低；热风是真实干热输入，不是坏数据。
- **修复**：用哈气触发 `OVER_HUMIDITY`，用热风触发 `OVER_TEMP`，两个分支分别验证。
- **防再发规则**：先按物理规律设计激励，再判断数据真伪；不要用错误的输入证明传感器坏了。
- **来源**：Day 99。

### 20. 野值排查顺序错误会白拆线

- **现象**：看到异常温湿度后首先怀疑接线/固件，排查成本高。
- **根因**：没有先判断静置基线是否稳定，也没有确认异常是否有物理来源。
- **修复**：稳定基线 -> 物理激励 -> 数据合理性 -> 最后查接线/固件。
- **防再发规则**：硬件异常按“基线、输入、协议、接线、器件”顺序排除，每步留证据。
- **来源**：Day 99。

### 21. DHT22 接近上限仍持续加热

- **现象**：热风实测 68°C，接近 DHT22 约 80°C 上限。
- **根因**：为快速触发温度报警而长时间近距离加热。
- **修复**：达到报警阈值后立即停止，避免永久损坏。
- **防再发规则**：传感器测试同时设置温度上限和时长上限；演示特写不追求极限值。
- **来源**：Day 99。

### 22. 持续超限生成报警风暴

- **现象**：采样每 2 秒一条，一次吹风产生 100+ 条同设备同类型告警。
- **根因**：当前只有逐条检测，没有“未恢复告警合并/去重”窗口。
- **修复**：测试后批量 resolved 226 条；产品级去重仍记技术债。
- **防再发规则**：报警系统必须有指纹、持续态、恢复态和合并窗口；演示数据要清理但不能把清理当修复。
- **来源**：Day 99，项目技术债。

### 23. 模拟器四个状态机/JSON 错误

- **现象**：payload 只有 `{}`、主程序提前退出、尖峰永不回落、首条状态误报故障。
- **根因**：JsonBuilder 缺根花括号、CompletableFuture 过早完成、spikeUntil 不递减、helper 参数错位。
- **修复**：修正根对象、由 stop 完成 future、逐轮递减尖峰、对齐离散点默认值。
- **防再发规则**：模拟器也必须做合法 JSON、状态序列和生命周期验收，不能把它当“假数据随便发”。
- **来源**：Day 95。

## 五、测试与测量

### 24. JMeter `Equals + Or` 把 HTTP 200 也判失败

- **现象**：突发组 1,576 个 200 全部 `success=false`。
- **根因**：`ResponseAssertion test_type=72` 与两个 pattern 的组合语义不符合预期。
- **修复**：改为 Matches 正则 `(200|429)`，按响应码和 failureMessage 交叉复核。
- **防再发规则**：断言本身也要有通过/失败样本验证，不能只看错误百分比。
- **来源**：Day 102，`backend/performance/README.md`。

### 25. JMeter 默认把 4xx 记为 error

- **现象**：突发组 Err 占比 99%+，看起来像应用全面故障。
- **根因**：429 是限流器的预期输出，但 JMeter 默认把 4xx 标为 `success=false`。
- **修复**：从 JTL `responseCode` 统计 200/429，不读 summariser 的 Err 当业务成功率。
- **防再发规则**：性能报告的“成功”必须定义：协议成功、业务成功、预期拒绝要分栏。
- **来源**：Day 102。

### 26. JMeter UDV 静默吞掉 `-J` 覆盖

- **现象**：命令行把持续时间改短，实际仍按 60/60/30 秒跑满。
- **根因**：UDV 与 `-J` 属性同名，`${readDuration}` 优先解析 UDV。
- **修复**：使用 `${__P(readDuration,60)}` 并删除同名 UDV。
- **防再发规则**：参数化后打印最终属性值；脚本改动先用短时试跑确认覆盖生效。
- **来源**：Day 102。

### 27. throughput timer 不接受属性表达式

- **现象**：JMX 直接加载失败，XStream 抛 `NumberFormatException`。
- **根因**：`ConstantThroughputTimer.doubleProp` 只接受字面数字。
- **修复**：保留字面值，脚本生成临时副本时替换数字。
- **防再发规则**：JMeter 每个组件支持的参数类型不同，不把 EL/属性语法当成万能。
- **来源**：Day 102。

### 28. p99 跨运行“改善”其实是分母变化

- **现象**：突发 p99 从 504ms 降到 10ms，看似巨大优化。
- **根因**：慢样本都是 1,505 条，占比从 1.082% 降到 0.972%，跨过 99% 分位边界。
- **修复**：报告同时给出慢样本绝对条数、总样本数和按响应码拆分结果。
- **防再发规则**：分位数只描述位置，不描述尾部规模；性能结论必须带绝对计数。
- **来源**：Day 103。

### 29. 聚合分位数掩盖响应码差异

- **现象**：最初判断“429 被 `tryAcquire(500ms)` 阻塞 500ms”。
- **根因**：把 200 的背压等待混入所有响应；按 `responseCode` 拆分后 429 avg 0.9ms、p99 3ms。
- **修复**：Day 103 公开更正 Day 102 结论；Guava `tryAcquire(timeout)` 等待不足时立即返回。
- **防再发规则**：任何聚合指标先问“由哪些分组构成”，再下因果结论。
- **来源**：Day 102-103，ADR 0037。

### 30. 删除正在写的 slow.log 得到伪“0 条慢查询”

- **现象**：定位 SQL 尾部延迟时，slow.log 显示没有慢查询。
- **根因**：文件被 `rm` 后 MySQL 继续写已删除 inode，新路径不再出现该文件。
- **修复**：恢复日志并用 `SELECT SLEEP(0.25)` 对照组证明慢查询仪器会记录。
- **防再发规则**：任何“没有发现”的结论，先做阳性对照证明仪器在工作。
- **来源**：Day 103。

### 31. 管道和后台任务吞掉测试失败

- **现象**：`./mvnw test | tail` 只看到尾部，管道退出码掩盖 Maven 失败。
- **根因**：命令链退出码取最后一个进程，且输出被截断。
- **修复**：保留完整日志，再 grep/summarize；必要时启用 `pipefail`。
- **防再发规则**：全量回归以 BUILD SUCCESS 和 surefire 汇总为准，不以“终端没红字”为准。
- **来源**：Day 100。

### 32. 全 mock 全绿不等于 E2E

- **现象**：Segment 级测试全绿，但 Producer -> MQ -> Consumer -> Redis -> DLQ 从未真实串联。
- **根因**：每段都 mock 外部依赖，测试只证明单段调用，不证明协议和基础设施行为。
- **修复**：新增 opt-in `it` profile，真实 RabbitMQ/Redis 覆盖幂等与 DLQ 3 个用例。
- **防再发规则**：关键链路至少有独立真实 IT；默认单测与显式 E2E 分层报告。
- **来源**：Day 91 Exit Audit，ADR 0032。

## 六、AI、MCP 与工具边界

### 33. Spring AI 自动工具循环没有轮次上限

- **现象**：模型持续请求工具时，自动执行会递归直至模型停止，无法约束成本。
- **根因**：`internalToolExecutionEnabled=true` 的生命周期掌握在框架内部。
- **修复**：关闭自动循环，业务手写 `while + execute + append`，设置 3 轮硬限和收尾调用。
- **防再发规则**：任何 Agent 必须有轮次、超时、工具白名单、只读边界和 trace 五类约束。
- **来源**：Day 68，ADR 0023 §5。

### 34. 不同 Agent 的轮次硬限不能机械复制

- **现象**：设备问答 3 轮合理，但巡检需列设备、查状态、查数据、查告警并收尾。
- **根因**：任务复杂度不同，统一硬限会导致日报提前截断。
- **修复**：单设备默认 3 轮；多步分析最多 4 轮；MCP 巡检 6 轮，全部保留 `truncated` 证据。
- **防再发规则**：轮次按任务路径预算，不以“越大越智能”调参；超限必须显式可见。
- **来源**：ADR 0023/0026、Day 79/83。

### 35. MCP 自动收集所有 ToolCallback，越权面不可见

- **现象**：内部依赖 `ToolContext.userId` 的工具可能进入无身份 MCP 通道，调用只会 403。
- **根因**：Spring AI MCP Server 自动配置会收集容器内工具，默认不等于最小暴露。
- **修复**：`McpToolConfig` 显式注册仅 7 个 MCP 只读工具，内部 Agent 工具不暴露。
- **防再发规则**：工具通道按身份能力分组；新增工具先问“谁调用、带不带 userId、是否只读”。
- **来源**：Day 80，ADR 0027/0028。

### 36. MCP 客户端打通后仍需要独立鉴权边界

- **现象**：协议握手和 listTools 成功，不代表端点适合公网开放。
- **根因**：MCP 1.0 没有标准 HTTP 鉴权头，工具本身也没有用户身份。
- **修复**：可选 `X-MCP-Token` 传输门 + 内网可信边界 + REST 入口 ADMIN 审计。
- **防再发规则**：协议能力、身份认证、业务授权分开评审；开发默认放行必须在文档中写明。
- **来源**：Day 82，ADR 0029。

### 37. LLM JSON 围栏和超长输出污染解析

- **现象**：模型回复带 ```json 围栏或结构字段漂移，业务解析异常。
- **根因**：自然语言输出不能直接当严格 JSON transport。
- **修复**：统一 `AiJsonFallbackUtil` 去围栏、2 MB 上限、解析失败回退；提示词约束结构化字段。
- **防再发规则**：模型输出永远按不可信输入处理；严格 DTO/校验、大小上限、降级路径三者齐全。
- **来源**：Day 89。

### 38. AI 未启用时不能拖垮核心业务

- **现象**：无 DeepSeek Key 的环境若强依赖 AI Bean，会导致应用无法启动。
- **根因**：外部付费能力被当成核心依赖。
- **修复**：`DEEPSEEK_ENABLED=false` 默认关闭，AI 端点按需返回 503，设备/告警/数据链路照常。
- **防再发规则**：外部模型一律 opt-in；核心链路通过接口隔离并可降级。
- **来源**：ADR 0021。

## 七、构建、编排与部署

### 39. 修改 Compose bind-mount 配置后没有重启容器

- **现象**：更新 `prometheus/prometheus.yml` 后抓取目标仍未变化。
- **根因**：bind mount 内容更新不会触发容器重建或进程重载。
- **修复**：`docker compose restart prometheus` 后双 target 正常。
- **防再发规则**：配置挂载变更按“文件校验 -> restart -> target 验证”执行。
- **来源**：Day 104。

### 40. MinIO 旧固定 tag 已从 Docker Hub 下架

- **现象**：`RELEASE.2025-09-07T16-13-09Z` 无法 pull，新环境一键编排中断。
- **根因**：社区镜像迁移/下架，历史 tag 不再公开提供。
- **修复**：本地同版本 `latest` 核实后 retag；新环境需 quay.io 或离线导入。
- **防再发规则**：生产/交付固定 digest 或保留离线包；部署前验证镜像源可用，不只验证 tag 名。
- **来源**：Day 104，Infrastructure Baseline V1.6。

### 41. Docker Hub 瞬时超时被误判为配置错误

- **现象**：基础镜像首次拉取 i/o timeout，重试即成功。
- **根因**：网络抖动，不是镜像名或认证错误。
- **修复**：原样重试一次，再判断是否需要换源。
- **防再发规则**：区分 transient failure 和 deterministic failure；不要为了网络抖动立刻改稳定配置。
- **来源**：Day 104。

### 42. BuildKit 无缓存时依赖下载耗时异常

- **现象**：容器构建 4-5 分钟，看起来像卡死。
- **根因**：BuildKit 缓存 0B，Maven `dependency:go-offline` 全量下载。
- **修复**：等待首轮完成，后续复用缓存。
- **防再发规则**：报告构建耗时同时标注 cache 状态；排障先看下载进度而非直接杀进程。
- **来源**：Day 104。

### 43. JMeter 与项目运行 JDK 混用

- **现象**：JMeter 5.6.3 在 JDK 25 有 Unsafe 弃用告警，执行稳定性无保证。
- **根因**：压测工具官方支持版本与项目运行时不同。
- **修复**：脚本默认选择 Corretto 17，`JMETER_JAVA_HOME` 可覆盖。
- **防再发规则**：应用运行时和测试工具运行时分别列出支持矩阵，不默认“Java 向上兼容”。
- **来源**：Day 102。

## 最小排障顺序

1. **先证明信号存在**：订阅端在线、请求到达、日志有 traceId、落库有条数增量。
2. **再证明仪器有效**：阳性对照、已知成功样本、响应码拆分。
3. **再缩小边界**：外部依赖 -> 配置 -> 应用 -> 数据 -> 硬件。
4. **修复后复测同一指标**：保留修复前绝对数，避免百分比和分位数制造假改善。
5. **最后固化为测试或 Runbook**：没有自动化守卫的经验，下一次仍会复发。
